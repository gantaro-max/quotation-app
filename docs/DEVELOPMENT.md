# 開発プロセス

本プロジェクトは、要件定義・設計と実装を役割分担する形でAIアシスタントを使い分けて開発している。

各エージェントは起動時にリポジトリ直下の指示ファイルを自動で読み込む(Claude Codeは [CLAUDE.md](../CLAUDE.md)、Codexは [AGENTS.md](../AGENTS.md))。両ファイルとも本ドキュメントへのリンクを軸にした最小限の内容にとどめ、詳細ルールは本ドキュメントに一本化する(重複記載によるトークン増加を避けるため)。役割やルールを変更する場合は本ドキュメントを更新し、CLAUDE.md/AGENTS.mdは「要約」部分のみ必要に応じて追従させる。

## 開発体制

| 役割 | 担当 | 責任範囲 |
| :--- | :--- | :--- |
| 要件定義・基本設計・テスト方針・最終レビュー | Claude Code (Opus 5, high effort) | 課題の発見、要件定義、DB/API設計方針の決定、テスト方針の策定、実装後の最終レビュー |
| 詳細設計・実装・テストループ | Codex (GPT-5.6 "Terra", medium effort。難所のみhigh) | 仕様書に基づく詳細設計、TDDでのコーディング、テストコード作成・実行・修正の反復 |

この分担は、要件が曖昧なまま実装に着手して手戻りが発生することを防ぎ、実装側は仕様に集中できるようにするためのもの。

## 仕様書 (docs/specs/) の運用ルール

修正・追加のうち、コード実装を伴うものは着手前に `docs/specs/NNN-短い英語スラッグ.md` として仕様書を作成する。`NNN` は3桁の連番（例: `001`, `002`）で、作成順に採番する。ドキュメント修正のみで完結するタスク（誤字修正、READMEの整理など）は仕様書を作らずに直接修正してよい。

### 粒度・トークン効率化の原則

AIエージェント同士の引き継ぎはコンテキスト（トークン）を消費するため、以下を徹底する。

- **1仕様書 = 1つの独立して完結するタスク。** 無関係な変更を1つの仕様書にまとめない。関連の薄い修正はNNNを分けて別ファイルにする。実装が一度のセッションで収まらないほど大きい場合は、仕様書自体を分割する。
- **重複記載をしない。** `docs/REQUIREMENTS.md` / `docs/DATABASE.md` に既に書かれている内容は転記せず、リンクで参照する。
- **コード全文を貼らない。** 該当箇所は `ファイルパス:行番号`（例: `backend/.../QuotationService.java:229-236`）で示し、必要最小限の抜粋のみ引用する。
- **対象ファイルリストを絞る。** 「基本設計」に触るファイルを明記し、Codexが無関係なファイルを探索して読みに行く手間（＝トークン消費）を減らす。
- **レビューは差分ベースで行う。** Claude Codeによる最終レビューは `git diff` / `git log` で変更点のみを確認し、変更していないファイルまで読み直さない。
- **仕様書自体は簡潔に。** 前置きや背景説明は要点のみとし、表・チェックリストを多用して文章量を抑える。

### 仕様書のテンプレート構成

1. タイトル・ステータス・担当
2. 背景・課題
3. 要件
4. 基本設計（DBスキーマ、バックエンド、フロントエンドへの影響を明記）
5. テスト方針（**Given-When-Then 形式で、そのままテストコードに落とせる粒度で記述する**。下記「テスト駆動開発」参照）
6. 受け入れ基準（チェックリスト形式。テスト方針の各ケースと1対1で対応させる）
7. スコープ外（やらないことを明記し、実装時の範囲逸脱を防ぐ）

既存の [SPEC-001](specs/001-user-branch-id.md)・[SPEC-002](specs/002-remove-unused-copy-api.md) を参考にすること。

### ステータスの遷移

| ステータス | 意味 |
| :--- | :--- |
| 未着手 | Claude Codeが仕様を書いた段階。Codexへの引き継ぎ待ち |
| 実装中 | Codexが詳細設計・実装・テストループを実施中 |
| レビュー中 | 実装完了、Claude Codeによる最終レビュー待ち |
| 完了 | レビュー済み。受け入れ基準を全て満たし、`docs/REQUIREMENTS.md` 等の関連ドキュメントも更新済み |
| 却下・保留 | 対応しないと判断、または後回しにした場合。理由を仕様書に追記する |

## テスト駆動開発 (TDD) のルール

実装はテストファーストで行う。

1. **Red:** 仕様書の「テスト方針」に書かれたケースを、まず失敗するテストコードとして書く。受け入れ基準の各項目に対応するテストが最低1つ存在すること。
2. **Green:** そのテストを通す最小限の実装を書く。過剰な作り込み・先回りの抽象化はしない。
3. **Refactor:** テストが通った状態を保ったまま、重複排除・命名整理などの整理を行う。
4. 受け入れ基準の項目数だけ、この Red → Green → Refactor を繰り返す。
5. **実装コードとテストコードは同一コミットに含める。** テストの無い実装コミットを作らない。
6. Claude Codeによる最終レビューでは、受け入れ基準の各項目に対応するテストが実際に存在し、実装前の時点でそのテストが失敗する内容だったこと（＝後付けのテストでないこと）を確認する。

## 引き継ぎ・レビューの流れ

1. **課題発見・要件定義（Claude Code）**: 不整合や不足機能を発見し、`docs/specs/` に仕様書を作成。テスト方針をGiven-When-Then形式で記述する。ステータスは「未着手」。
2. **実装（Codex）**: 仕様書を読み、詳細設計を行った上でTDDサイクル（Red→Green→Refactor）を受け入れ基準の項目ごとに繰り返す。仕様書のステータスを「実装中」に更新し、実装完了後「レビュー中」にする。仕様に無い作業（スコープ外に書かれた内容や、無関係なリファクタリング）は行わない。仕様に疑問がある場合はコードに反映する前にClaude Codeに確認する。
3. **最終レビュー（Claude Code）**: 受け入れ基準を満たしているか、対応するテストが存在するか、仕様からの逸脱がないかを確認する。関連ドキュメント（`docs/REQUIREMENTS.md`、`docs/DATABASE.md` 等）が実装後の状態と一致するよう更新する。問題なければ仕様書のステータスを「完了」にする。

## コミット・push運用

- コミットメッセージ、ブランチ運用は特に規定を設けず、通常のGit運用に従う。
- 現状 `main` ブランチに直接コミットする運用。機密情報（DB接続情報、APIキー、実顧客・実社員データ）は絶対にコミットしない（[docs/DATABASE.md](DATABASE.md) 参照、環境変数での設定を徹底する）。

## 遵守事項（すべきこと・してはいけないこと）

CLAUDE.md / AGENTS.md からもこのセクションを参照する。いずれも本プロジェクトで実際に問題になった、または問題になり得ることに基づく。

### してはいけないこと

- **実顧客データ・実社員データ・パスワード・APIキーなど機密情報をコミットしない。** コード・ドキュメント・テストデータのいずれにも書かない。過去にこれが原因で全コミット履歴の書き換えが発生している。
- **仕様書 (`docs/specs/`) のないコード変更に着手しない。** ドキュメントのみの軽微な修正（誤字修正等）を除く。
- **仕様書の「スコープ外」に書かれた作業、依頼されていない周辺リファクタリングをしない。**
- **テストの無い実装コミットを作らない。** TDDサイクル(Red→Green→Refactor)を飛ばさない。
- **`git push --force` / `git reset --hard` / `git filter-repo` など履歴を書き換える操作を、都度の明示的なユーザー承認なしに実行しない。** 過去に機密データ除去のため一度実施しているが、これは例外的対応であり「前例があるから今回も無承認でよい」とはみなさない。
- **pre-commit等のフックを `--no-verify` で回避しない。**
- **既存のAPI契約・DBスキーマ・UXフローを、仕様書に書かれていない形で無断変更しない。**
- **動作確認していない変更を「完了」として報告しない。**

### すべきこと

- 実装前に対応する `docs/specs/` の仕様書を確認する。無ければ先に仕様書を作成する(Codexの場合はClaude Codeへの仕様書作成依頼をユーザーに伝える)。
- コミット前に `git status` / `git diff` で差分を確認し、機密情報や意図しないファイルが含まれていないか確認する。
- TDDサイクル(Red→Green→Refactor)に従う。
- 実装後、`docs/REQUIREMENTS.md` ・ `docs/DATABASE.md` など関連ドキュメントを実装内容に合わせて更新する。
- 破壊的操作(force push, DB DROP, リセット系コマンド等)の前に、対象と影響範囲を明示してユーザーに確認する。
- シークレットは環境変数経由で扱う(`${GEMINI_API_KEY}` のようなプレースホルダをコードに残す)。
- 仕様・要件に疑問点がある場合、憶測で進めずユーザーまたはClaude Codeでのレビューで確認する。
- 仕様書のステータスを進捗に応じて更新する。
